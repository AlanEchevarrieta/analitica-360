¿Qué es este producto?

Una aplicación web SaaS multi-tenant mobile-first que permite a pequeños comercios y emprendedores registrar ventas, compras, productos y proveedores desde el celular. Los datos se almacenan en Supabase (PostgreSQL) y se analizan en Power BI. Cada cliente ve únicamente sus propios datos.

Stack tecnológico — no negociable

  • Frontend: React + Tailwind CSS — mobile-first, PWA
  • Base de datos: Supabase (PostgreSQL) con Row Level Security
  • Autenticación: Supabase Auth (email + contraseña)
  • Deploy: Vercel (automático en cada push)
  • Analytics: Power BI conectado a Supabase vía PostgreSQL

Empresas de referencia que usan este stack

Supabase es usado en producción por Mozilla, 1Password, Replicate, y cientos de startups de Y Combinator. Es el backend preferido de AI coding tools como Cursor, Bolt y Lovable. Valoración actual: $2B USD. ARR estimado: $170M USD (mayo 2026). No es un experimento — es infraestructura probada.

Principios de diseño — NUNCA violar estos

  • Nunca borrar físicamente — siempre usar deleted_at TIMESTAMP (borrado lógico)
  • Nunca sobreescribir precios — siempre insertar nueva fila en precios_historial
  • RLS desde el día 1 — cada tabla tiene política de aislación por empresa_id
  • Snapshot de precios en ventas — guardar precio_unitario y costo_unitario al momento de la venta
  • Stock calculado, no almacenado — compras - ventas en Power BI, no columna de stock
  • empresa_id en todas las tablas transaccionales — sin excepción
  • Variables de entorno para credenciales — nunca hardcodear en el código

-- TABLA: ventas (snapshot de precio al momento)
-- ═══════════════════════════════════════════
CREATE TABLE ventas (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  empresa_id      UUID NOT NULL REFERENCES empresas(id),
  producto_id     UUID NOT NULL REFERENCES productos(id),
  usuario_id      UUID NOT NULL REFERENCES usuarios(id),
  fecha           TIMESTAMPTZ NOT NULL DEFAULT now(),
  cantidad        INTEGER NOT NULL CHECK (cantidad > 0),
  precio_unitario NUMERIC(12,2) NOT NULL CHECK (precio_unitario >= 0),
  costo_unitario  NUMERIC(12,2) NOT NULL CHECK (costo_unitario >= 0),
  descuento       NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (descuento >= 0),
  forma_pago      TEXT NOT NULL
                  CHECK (forma_pago IN ('efectivo','transferencia','debito','credito','qr')),
  subtotal        NUMERIC(12,2) GENERATED ALWAYS AS
                  ((precio_unitario * cantidad) - descuento) STORED,
  notas           TEXT,
  deleted_at      TIMESTAMPTZ
);
CREATE INDEX idx_ventas_empresa_fecha ON ventas(empresa_id, fecha DESC);

Venta multi-línea — estructura correcta

Una venta puede tener múltiples productos. Se divide en dos tablas: el encabezado y las líneas.

-- ENCABEZADO DE VENTA (el "ticket")
CREATE TABLE ventas (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  empresa_id      UUID NOT NULL REFERENCES empresas(id),
  usuario_id      UUID NOT NULL REFERENCES usuarios(id),
  cliente_id      UUID REFERENCES clientes(id), -- opcional
  fecha           TIMESTAMPTZ NOT NULL DEFAULT now(),
  forma_pago      TEXT NOT NULL CHECK (forma_pago IN (
                    'efectivo','transferencia','debito',
                    'credito','qr')),
  descuento       NUMERIC(12,2) NOT NULL DEFAULT 0,
  canal           TEXT DEFAULT 'mostrador',
  notas           TEXT,
  deleted_at      TIMESTAMPTZ
);

-- LÍNEAS DE VENTA (los ítems del ticket)
CREATE TABLE ventas_items (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  venta_id        UUID NOT NULL REFERENCES ventas(id),
  empresa_id      UUID NOT NULL REFERENCES empresas(id),
  producto_id     UUID NOT NULL REFERENCES productos(id),
  cantidad        INTEGER NOT NULL CHECK (cantidad > 0),
  precio_unitario NUMERIC(12,2) NOT NULL,
  costo_unitario  NUMERIC(12,2) NOT NULL, -- snapshot del costo
  subtotal        NUMERIC(12,2) GENERATED ALWAYS AS
                  (precio_unitario * cantidad) STORED
);
CREATE INDEX idx_ventas_items_venta ON ventas_items(venta_id);
CREATE INDEX idx_ventas_items_empresa ON ventas_items(empresa_id);

Total de la venta en Power BI:

Total Venta =
CALCULATE(SUM(ventas_items[subtotal])) - MAX(ventas[descuento])
Impacto en movimientos_inventario: cuando se confirma una venta, la app inserta automáticamente un movimiento tipo venta con signo -1 por cada ítem. Si la venta tiene 3 ítems distintos → 3 movimientos en el Kardex. Si se anula la venta → se anulan los 3 movimientos.

El operador agrega ítems uno por uno. Cada ítem autocompleta el precio desde precios_historial. El descuento es en pesos, no porcentaje. El total se actualiza en tiempo real. Un solo toque en "Confirmar" guarda el encabezado, todas las líneas, y los movimientos de inventario correspondientes.

RLS — Políticas de seguridad CRÍTICO

-- ═══════════════════════════════════════════
-- FUNCIÓN ATÓMICA: registrar_venta()
-- Previene race conditions con FOR UPDATE
-- ═══════════════════════════════════════════
CREATE OR REPLACE FUNCTION registrar_venta(
  p_venta_id    UUID,
  p_empresa_id  UUID,
  p_usuario_id  UUID,
  p_forma_pago  TEXT,
  p_descuento   NUMERIC,
  p_canal       TEXT,
  p_items       JSONB   -- [{producto_id, variante_id, cantidad, precio, costo}]
) RETURNS UUID AS $$
DECLARE
  v_item       JSONB;
  v_stock_act  INTEGER;
  v_total      NUMERIC := 0;
BEGIN
  -- Validar descuento no negativo
  IF p_descuento < 0 THEN
    RAISE EXCEPTION 'DESCUENTO_NEGATIVO';
  END IF;

  -- Calcular total y validar
  SELECT SUM((item->>'precio')::NUMERIC * (item->>'cantidad')::INT)
  INTO v_total
  FROM jsonb_array_elements(p_items) item;

  IF (v_total - p_descuento) <= 0 THEN
    RAISE EXCEPTION 'DESCUENTO_MAYOR_TOTAL';
  END IF;

  -- Insertar encabezado de venta
  INSERT INTO ventas (id, empresa_id, usuario_id, forma_pago, descuento, canal)
  VALUES (p_venta_id, p_empresa_id, p_usuario_id, p_forma_pago, p_descuento, p_canal);

  -- Procesar cada ítem con bloqueo de stock
  FOR v_item IN SELECT * FROM jsonb_array_elements(p_items)
  LOOP
    -- Bloquear fila para evitar race condition
    SELECT COALESCE(SUM(cantidad * signo), 0) INTO v_stock_act
    FROM movimientos_inventario
    WHERE producto_id = (v_item->>'producto_id')::UUID
      AND empresa_id = p_empresa_id
      AND deleted_at IS NULL
    FOR UPDATE;

    -- Insertar ítem de venta
    INSERT INTO ventas_items (venta_id, empresa_id, producto_id, variante_id, cantidad, precio_unitario, costo_unitario)
    VALUES (
      p_venta_id, p_empresa_id,
      (v_item->>'producto_id')::UUID,
      (v_item->>'variante_id')::UUID,
      (v_item->>'cantidad')::INT,
      (v_item->>'precio')::NUMERIC,
      (v_item->>'costo')::NUMERIC
    );

    -- Insertar movimiento de inventario
    INSERT INTO movimientos_inventario (
      empresa_id, producto_id, variante_id, usuario_id,
      tipo, signo, cantidad, precio_unitario, costo_unitario,
      referencia_id
    ) VALUES (
      p_empresa_id, (v_item->>'producto_id')::UUID,
      (v_item->>'variante_id')::UUID, p_usuario_id,
      'venta', -1, (v_item->>'cantidad')::INT,
      (v_item->>'precio')::NUMERIC, (v_item->>'costo')::NUMERIC,
      p_venta_id
    );
  END LOOP;

  RETURN p_venta_id;
END; $$ LANGUAGE plpgsql SECURITY DEFINER;

-- Función helper: obtener empresa_id del usuario autenticado
CREATE OR REPLACE FUNCTION get_empresa_id()
RETURNS UUID AS $$
  SELECT empresa_id FROM usuarios
  WHERE id = auth.uid()
  LIMIT 1;
$$ LANGUAGE sql SECURITY DEFINER STABLE;

-- Función helper: obtener rol del usuario autenticado
CREATE OR REPLACE FUNCTION get_rol()
RETURNS TEXT AS $$
  SELECT rol FROM usuarios
  WHERE id = auth.uid()
  LIMIT 1;
$$ LANGUAGE sql SECURITY DEFINER STABLE;

Flujo de autenticación

1
Usuario entra a la app → ve pantalla de login (email + contraseña)
2
Supabase Auth valida credenciales y devuelve JWT con el user ID
3
La app consulta la tabla usuarios con ese user ID para obtener empresa_id y rol
4
Ese contexto (empresa_id + rol) se guarda en el estado global de la app (React Context)
5
Todas las consultas a Supabase incluyen automáticamente el filtro de empresa via RLS
6
La UI muestra u oculta opciones según el rol (dueño ve todo, operador solo carga, visor solo ve)
Cada módulo se desarrolla, prueba y aprueba por separado antes de pasar al siguiente. Este es el orden recomendado.
1
Auth + Alta de empresa
PRIMERO

Qué hace: login, registro de empresa nueva, creación del primer usuario dueño.

Pantallas: Login, Registro de empresa (nombre, rubro), confirmación.

Validaciones: email válido, contraseña mínimo 8 caracteres, nombre de empresa obligatorio.

Qué genera en la BD: fila en empresas + fila en usuarios con rol dueno + fila en historial_planes.

Criterio de aprobación: usuario puede registrarse, iniciar sesión y cerrar sesión. Otro usuario no puede ver sus datos.

2
Productos + Historial de precios
FASE 1

Qué hace: ABM de productos y carga de precios con historial.

Pantallas: Lista de productos (con buscador), formulario de producto nuevo, formulario de actualización de precio.

Campos producto: nombre (obligatorio), categoría, variante (color/talle/modelo), activo.

Campos precio: precio_venta (obligatorio, > 0), costo (obligatorio, ≥ 0), fecha_desde (default hoy).

Regla crítica: actualizar precio = INSERT en precios_historial, NUNCA UPDATE del precio anterior.

Criterio de aprobación: crear producto, actualizar precio 3 veces, verificar que el historial tiene 3 filas y la app muestra el precio más reciente.

3
Ventas
FASE 1

Qué hace: registro de ventas desde el celular en máximo 3 toques.

Pantallas: botón grande "Nueva venta" en home → selector de producto (dropdown con autocompletado) → cantidad → forma de pago (4 botones grandes) → confirmar.

Campos: producto_id, cantidad (mínimo 1), fecha (default ahora, editable), forma_pago, descuento (opcional), notas (opcional).

Comportamiento: al seleccionar producto, autocompletar precio_unitario y costo_unitario desde precios_historial (precio más reciente con fecha_desde ≤ hoy).

Formas de pago: botones — Efectivo 💵, Transferencia 📱, Débito 💳, Crédito 💳, QR 📷.

Criterio de aprobación: registrar venta en menos de 15 segundos desde el celular. Precio y costo se autocompletaron correctamente. La venta aparece en el historial.

4
Compras + Proveedores
FASE 2

Qué hace: registro de compras a proveedores y ABM de proveedores.

Campos compra: producto_id, proveedor_id (opcional), cantidad, costo_total, fecha (editable para cargar compras atrasadas), notas.

Costo unitario: calculado automáticamente = costo_total / cantidad. No lo ingresa el usuario.

Campos proveedor: nombre (obligatorio), contacto, condiciones_pago, notas.

Criterio de aprobación: registrar compra con fecha pasada. Verificar que el stock calculado (compras - ventas) refleja la compra retroactiva correctamente.

5
Gestión de usuarios
FASE 2

Qué hace: el dueño puede crear, editar y desactivar usuarios de su empresa.

Pantallas: lista de usuarios, formulario de invitación (email + rol), confirmación.

Flujo de invitación: dueño ingresa email → Supabase Auth envía email de invitación → usuario crea contraseña → fila en usuarios con empresa_id y rol asignado.

Criterio de aprobación: invitar usuario operador, verificar que puede cargar ventas pero no editar productos. Invitar usuario visor, verificar que solo puede ver.

6
Dashboard básico (Plan Starter)
FASE 2

Qué hace: resumen visual simple de ventas del día, la semana y el mes.

KPIs: total vendido hoy, total vendido esta semana, top 3 productos del mes, distribución por forma de pago.

Tecnología: Recharts (librería de gráficos para React, sin costo).

Criterio de aprobación: los números del dashboard coinciden con la suma manual de las ventas cargadas.

Estos escenarios deben probarse antes de aprobar cada módulo. Cubren los casos edge más comunes en negocios reales argentinos.

Escenarios de prueba — Ventas

E1 — Venta normal
Cargar venta de 1 canasto chico a $25.000 en efectivo. Verificar que el subtotal = $25.000 y el costo_unitario se autocompletó desde precios_historial.
E2 — Venta con descuento
Cargar venta de 2 mochilas a $30.000 c/u con descuento de $5.000. Verificar que subtotal = (30.000 × 2) - 5.000 = $55.000.
E3 — Venta con fecha pasada
Cargar venta de ayer. Verificar que el precio que se autocompleta es el que estaba vigente ayer, no el de hoy si hubo actualización.
E4 — Venta con cantidad 0
Intentar cargar venta con cantidad 0. La app debe rechazarla con mensaje claro: "La cantidad debe ser al menos 1".
E5 — Dos usuarios en simultáneo
Dos sesiones abiertas en simultáneo (operador 1 y operador 2) cargan ventas al mismo tiempo. Verificar que ambas aparecen en el historial sin conflicto.
E6 — Aislación entre empresas
Loguear como empresa A. Intentar acceder manualmente a datos de empresa B (modificando la URL o haciendo consulta directa). Supabase debe devolver array vacío, nunca datos de otra empresa.

Escenarios de prueba — Stock y compras

E7 — Stock negativo por compras faltantes

Cada error tiene una solución diseñada desde la base de datos. Nunca se borra — siempre se corrige con trazabilidad completa.

Principio central de correcciones

Regla de oro: nunca se borra un registro. Siempre se corrige con un movimiento inverso o una anulación trazada.

En la base de datos, una anulación es simplemente poner deleted_at = now() en el registro original y generar el movimiento compensatorio. La historia queda intacta, el efecto queda revertido.

Error 1 — Venta con cantidad incorrecta

EscenarioVendí 10 mates marrones, era 1.
SoluciónEl usuario busca la venta en el historial → toca "Anular" → la app marca deleted_at en esa venta y genera movimiento +10 (devolucion_cliente) con motivo "Anulación por error de cantidad" → el usuario crea venta nueva de 1 unidad.
En la BD quedaVenta original (anulada) + movimiento inverso +10 + venta correcta de 1. Stock neto correcto. Trazabilidad completa.
Quién puede hacerloSolo rol dueño. Los operadores no pueden anular.
Límite de tiempoConfigurable por empresa. Recomendado: solo se puede anular ventas del mismo día o de las últimas 24hs. Después requiere ajuste manual con motivo.

Error 2 — Venta con producto incorrecto

EscenarioSeleccioné "Canasto Grande" en lugar de "Canasto Chico".
SoluciónIgual que Error 1. Anulación + nueva venta con el producto correcto. No existe "editar una venta" — solo anular y recrear.
PrevenciónPantalla de confirmación antes de guardar: "¿Confirmás la venta de 1 x Canasto Chico a $25.000 en efectivo?" con foto del producto si está disponible.

Error 3 — Compra cargada con costo incorrecto

EscenarioCargué compra de 10 bolsos a $100.000 total. Era $1.000.000.
SoluciónAnular la compra original (deleted_at) + movimiento inverso −10 + nueva compra con el costo correcto. El costo_unitario se recalcula solo.
ImpactoEl margen calculado en Power BI va a reflejar el costo correcto desde el momento de la corrección. Las ventas anteriores a la corrección mantienen el snapshot de costo que tenían al momento de venderse.

Error 4 — Precio mal actualizado

EscenarioActualicé el precio a $2.500 cuando era $25.000. Error de tipeo.
SoluciónSimplemente cargás el precio correcto ($25.000). Se inserta nueva fila en precios_historial con fecha de hoy. Las ventas que se hicieron con el precio erróneo de $2.500 ya tienen el snapshot guardado — no se pueden cambiar retroactivamente (correcto, es lo que pasó).
PrevenciónAl actualizar precio, mostrar: "El precio anterior era $25.000. Estás cambiando a $2.500. ¿Confirmar?" Si la variación es mayor al 50%, pedir confirmación doble.

Error 5 — Producto duplicado en el catálogo

Escenario"Canasto Chico" y "canasto chico" y "Canasto chico" son tres productos distintos por error de tipeo.
SoluciónFunción de "Fusionar productos": se elige el producto correcto y los duplicados, todos los movimientos de los duplicados se reasignan al producto correcto, los duplicados se marcan como inactivos.
PrevenciónAl crear un producto nuevo, la app busca nombres similares (búsqueda fuzzy) y avisa: "Ya existe 'Canasto Chico'. ¿Es el mismo producto?"

Error 6 — Stock negativo por ventas sin compras

EscenarioVendí 10 unidades pero nunca cargué la compra. Stock = −10.
SoluciónCargar la compra con la fecha real en que llegó la mercadería (campo fecha editable). El stock se corrige retroactivamente porque siempre se calcula sobre todos los movimientos.
Alerta preventivaPower BI muestra alerta cuando stock < 0: "Stock negativo en Canasto Chico — verificar si hay compras sin cargar."

Error 7 — Importación masiva con datos incorrectos

EscenarioEl CSV de 500 productos tenía 30 filas con errores (precio en texto, SKU vacío, etc.).
SoluciónLa importación nunca falla en bloque. Importa las 470 correctas, genera un CSV de errores con las 30 fallidas indicando el motivo de cada una. El usuario corrige el CSV y reimporta solo esas 30.
PrevenciónAntes de importar, la app hace una "vista previa" de las primeras 10 filas para que el usuario confirme que el formato es correcto.

Error 8 — Usuario cargó venta en la empresa equivocada

EscenarioImposible por diseño. Cada usuario pertenece a una sola empresa. El RLS bloquea cualquier intento de cargar en otra empresa.
Por quéLa función get_empresa_id() toma el empresa_id del usuario autenticado y lo inyecta automáticamente en cada INSERT. El usuario nunca elige en qué empresa carga — siempre es la suya.

Integraciones externas que agregan valor al producto. Algunas disponibles desde el arranque, otras para fases futuras.

ARCA (ex-AFIP) — integración de alto valor

ARCA tiene una API pública con web services REST y SOAP que permiten validar contribuyentes, consultar condición frente al IVA y emitir comprobantes electrónicos. Contabilium usa exactamente esta API. Vos podés hacer lo mismo.

Fase 1 — Validación de CUIT (implementable en semanas):
El usuario ingresa el CUIT del proveedor o cliente → la app consulta ARCA → autocompleta razón social y condición IVA (Responsable Inscripto, Monotributista, etc.). Costo de implementación: bajo. Valor percibido: muy alto.
Fase 2 — Factura electrónica (implementable en 1-2 meses):
El cliente vende → toca "Generar factura" → la app emite la factura en ARCA automáticamente con tipo A, B o C según corresponda. Requisito: cada empresa necesita su certificado digital de ARCA (trámite único, vos los acompañás). Diferencial brutal vs competencia.
Fase 3 — Libro IVA digital (futuro):
Generación automática del libro IVA ventas y compras en formato ARCA. Esto reemplaza trabajo del contador y es un servicio premium que podés cobrar separado.
Web services relevantes de ARCA: wsfe (Factura Electrónica), ws-sr-padron-a4 (Padrón de contribuyentes), wsbfe (Bienes de Uso). Todos tienen documentación pública en arca.gob.ar.

Mercado Pago — cobro integrado

Mercado Pago tiene SDK para React que permite generar links de pago o cobrar con QR desde la misma app. Al completar una venta, el cliente puede tocar "Cobrar con MP" y el sistema registra el pago automáticamente sin necesidad de que el operador lo cargue a mano.

Implementación: SDK de Mercado Pago Checkout Pro. El webhook de MP notifica a tu app cuando el pago se confirma → la app actualiza el movimiento en Supabase automáticamente.
Costo: MP cobra comisión por transacción (varía por plan del cliente). Vos no pagás nada extra de infraestructura.

Andreani / OCA — cotización de envíos

Con las dimensiones y peso cargados en el catálogo de productos, podés integrar la API de Andreani o OCA para cotizar el envío en tiempo real al momento de la venta. El cliente ve cuánto va a costar el envío antes de confirmar.

Fórmula base: peso a cotizar = MAX(peso_real, alto×ancho×largo/4000). Esto ya está en la base de datos cuando el cliente carga las dimensiones del producto.

Tiendanube / MercadoLibre — sincronización de ventas

Ambas plataformas tienen APIs para leer las ventas realizadas. Podés automatizar la importación masiva que hoy se hace por CSV: las ventas de Tiendanube o ML del día se importan solas a Supabase sin que el cliente haga nada.

Implementación: webhook o pull periódico (cada hora) que lee las órdenes nuevas y las inserta en movimientos_inventario con canal="tiendanube" o canal="mercadolibre".
Valor: elimina la carga manual de ventas web. El cliente solo carga las ventas físicas del mostrador.

WhatsApp Business API — alertas automáticas

Cuando el stock de un producto cae por debajo del stock_minimo, la app puede enviar un WhatsApp automático al dueño: "⚠️ Stock bajo: Canasto Chico — quedan 2 unidades. ¿Querés hacer un pedido a Tío Roberto?" con el contacto del proveedor prellenado.

Implementación: Supabase Edge Function que corre cada hora, detecta stocks bajos y envía mensajes via Twilio o Meta WhatsApp Business API.
Costo: Twilio cobra ~$0.005 USD por mensaje. Para un cliente con 10 alertas al mes = $0.05 USD.
El CRM no es un formulario que el cliente llena. Es un registro que el operador completa DESPUÉS de que el cliente se va. El cliente nunca sabe que existe. El objetivo es crear vínculos reales, no bases de datos frías.

Filosofía del módulo — CRM relacional, no transaccional

La mayoría de los CRMs capturan datos fríos: nombre, email, teléfono. Eso es útil pero no crea fidelidad. Este módulo captura datos cálidos: preferencias, gustos, contexto de vida, lo que el cliente contó sin saber que lo ibas a anotar. Es lo que hacen los mejores vendedores del mundo de forma intuitiva.

Principio central: el único dato "obligatorio" al crear un cliente es el apodo o nombre con el que lo vas a reconocer. Todo lo demás es opcional y se va completando con el tiempo de forma natural.

Doña Creta llega al stand. El operador busca su nombre → ve todas las notas → puede saludarla por nombre, preguntarle por la nieta, mostrarle primero los productos en marrón. Doña Creta siente que la conocen.

¿Por qué esto genera fidelidad real?

Hay un concepto en psicología del consumidor que se llama efecto de ser recordado. Cuando una empresa recuerda un detalle personal que vos mencionaste casualmente, el cerebro lo procesa como una señal de que esa persona te importa. No como marketing — como vínculo humano genuino.

Doña Creta no sabe que hay una base de datos. Ella solo sabe que la persona del stand se acordó que su nieta juega al rugby y que le gusta el marrón. Eso vale más que cualquier descuento. Es la diferencia entre un cliente que vuelve y uno que busca alternativas.

El dato más valioso que podés capturar es el nombre. Con eso solo, la próxima vez que venga podés saludarla por nombre. Eso ya es excepcional en una feria.

Los 4 errores críticos — resueltos en el diseño

1. Stock cero sin bloqueo: No bloquear la venta — mostrar advertencia y dejar decidir al dueño. La app no puede saber si el comerciante vendió físicamente antes de cargar el movimiento.
2. Descuento mayor al total: Deshabilitar botón "Confirmar" si total_neto ≤ 0. Validación en frontend Y en la función PostgreSQL registrar_venta().
3. Race condition en stock: Resuelto con función atómica registrar_venta() que usa FOR UPDATE para bloquear filas mientras procesa la transacción.
4. Variantes multiplican el catálogo: Resuelto con tabla producto_variantes. Un producto tiene múltiples variantes, cada una con su SKU y stock propio.
